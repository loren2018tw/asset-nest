# ADR-0019：觀測代理的共用認證碼（信任模型與可見性）

- 狀態：已接受
- 日期：2026-10-06

## 背景

本系統目前沒有登入驗證（`auth.rs` 是 no-op 插槽；使用者介面的登入認證另行處理）。觀測代理會從其他網段、甚至跨 internet 回報；入庫端點若完全開放，任何來源都能偽造觀測或灌資料。另一方面，誤設定或已被遺忘的舊代理若持續回報，會佔用頻寬並污染觀測；管理者需要看得見這種情形。

## 決策

- **單一共用認證碼**：後端安裝時隨機產生（`.env` 的 `AGENT_AUTH_CODE`）；代理安裝時輸入同一組；請求以 HTTP 標頭攜帶。後端未設定認證碼時，入庫端點一律拒絕（503）。
- **錯誤即拒收並可見化**：認證碼不符的請求不寫入任何觀測；以來源 IP 記錄嘗試（次數、首次／最後時間、自報名稱與版本），在「系統狀態」頁顯示，期滿清理。
- **正確但網段對應不到的代理**也不入庫：代理狀態照記，於「系統狀態」頁顯示「未對應」。
- **傳輸安全靠部署**：跨不可信網路時須以 TLS（反向代理）保護；系統 v1 不內建 TLS。
- 使用者介面登入認證不在本 ADR 範圍。

## 理由

- v1 管理面處於單一信任域；共用認證碼是零註冊流程、可立即落地的最小防護；撤銷與輪替＝兩邊一起改（文件明示代價）。
- 把「認證失敗」與「未對應」變成系統狀態頁上的訊號，而不是默默拒絕或默默寫入——這正是誤設定與遺留代理的可診斷之處。
- 觀測是唯讀影子層（ADR-0014）：認證碼洩漏的最壞情形是注入假觀測，不影響宣告資料。

## 後果

- 認證碼無法區分個別代理、無法逐台撤銷；未來若需要逐台憑證，得改代理安裝流程與狀態頁。
- 狀態頁需保存成功與失敗來源清單；失敗紀錄的來源 IP 採連線來源（忽略 XFF，沿用 peer 判定）。
- 代理端需明確定義 401 行為（記 log、依退避重試，不熱迴圈）。

## 修訂

- 2026-10-07（見 ADR-0022）：來源 IP 判定修訂為「連線來源為 loopback（本機反向代理）時採信 `X-Forwarded-For` 第一段；否則一律使用連線來源 IP」。原「忽略 XFF」於直連情境維持不變。
