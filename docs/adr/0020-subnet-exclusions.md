# ADR-0020：排除範圍——與 DHCP 位址池結構互斥、不推送 Kea

- 狀態：已接受
- 日期：2026-10-06

## 背景

網段中有部分位址供其他機制使用（例如 NAT 對外位址、特殊設備），不可指派給資產的 Interface。現行模型只有 DHCP 位址池（pool）代表「不可指派」，但 pool 的語意是「保留給 Kea 動態配發」，用來記錄 NAT 位址語意不符，且 IP 清單的 `available` 會把它們誤列為可用。另一方面，「保留」已是 Reservation（IP＋MAC 綁 Interface）的專詞，新概念若也叫「保留」必然混淆。

候選方向：（A）新增獨立概念「排除範圍」（excluded range），可多段、附選填用途說明；（B）擴充 pool 加類型欄位（動態／排除）；（C）以 Reservation 記錄。C 與 DHCP 保留混淆；B 讓「同步到 Kea」與「不與 Kea 互動」兩種語意混在同一實體，pool 的驗證與同步邏輯都要分岔。

## 決策

- 新增**排除範圍**：Subnet 內不可指派給 Interface 的 IPv4 位址範圍（起=迄表單一位址），供其他機制使用；詞彙見 `GLOSSARY.md`。
- **與 pool 結構互斥**：排除範圍不得與任一 pool 或其他排除範圍重疊（儲存即阻擋）。要在 pool 中挖洞＝拆成兩段 pool。
- **兩層行為**（ADR-0006）：新指派進排除範圍＝結構阻擋；排除範圍後加覆蓋既有指派＝允許儲存＋語意衝突 `IpInExcludedRange`，不自動解除。
- **觀測抑制**：排除範圍內的位址不標 `ObservedOnUnassigned`（「非法佔用 IP」）。NAT 等位址本來就會被 ARP 看到；其 MAC 可能是實體介面、VRRP／HSRP 虛擬 MAC，或雙機 HA 切換、虛擬化搬遷而變動，不可依賴。
- **不與 Kea 互動**：排除範圍不進同步計畫、不推送。因與 pool 互斥，Kea 的動態配發不可能落在排除位址。
- **IPv4 限定**（同 pool 限制）。
- 「排除」成為 IpAddress 新狀態；`available` 定義更新為「不在 pool、也不在排除範圍」。
- 另提供指派候選 API（`GET /api/v1/ip-candidates`）以前綴篩選可用位址；本 ADR 只約束「可用」＝未指派、非池內、非排除範圍（端點契約見 spec）。

## 理由

- 名稱與業界一致（Windows DHCP「exclusion range」），語意是「從可指派集合中排除」，不與 Reservation 混淆。
- 互斥保證「不可使用」在 asset-nest 與 Kea 兩側同時成立：若允許重疊，Kea 仍會把位址配發出去；若在同步時自動切 pool，asset-nest 的池與 Kea 的 pool 變一對多，ADR-0013 的嚴格對齊語意複雜化。拆 pool 的表達力已足夠。
- 不推送 Kea：Kea 沒有排除原語；互斥已足以保證正確性，同步邏輯不需分岔。
- 排除範圍是本系統的表達（「這些位址另有用途」），不是 DHCP 服務設定，與網段層設定（pool／gateway）本質不同。
- 觀測抑制避免 NAT 位址長期誤報「非法佔用」，讓「非法佔用」清單保持可信。

## 後果

- 網段 CSV（ADR-0009）新增第 6 欄「排除範圍」：多段以 `|` 分隔，每段 `起-迄`，用途說明以 `#` 接續（`起-迄#用途說明`）；舊檔相容（欄位可缺席）。用途說明不得含 `|`（分隔符）。
- IP 清單新增「排除」狀態與篩選；排除且未指派的列不可於 UI 指派。
- 既有指派被排除範圍覆蓋時顯示 `IpInExcludedRange`、不自動解除；若要讓 Kea 動態配發該位址，必須先調整 pool（結構驗證會要求拆 pool）。
- 排除範圍僅供本系統辨識與阻擋，維運者若直接改 Kea pool 仍可能造成漂移；由完整同步的嚴格對齊收斂（既有機制）。
- 未來若要在不拆 pool 的前提下讓 Kea 避開某範圍，需重新檢討本決策。
