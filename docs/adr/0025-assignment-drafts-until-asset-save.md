# ADR-0025：未儲存資產的指派以草稿延後至儲存時落地

- 狀態：已接受
- 日期：2026-10-11

## 背景

新增資產對話框中，介面在資產建立前只是本地草稿；指派 API（`PUT /assets/{id}/assignments`，見 ADR-0007）需要已存在的資產與介面 id，因此新增流程完全沒有指派入口，必須「先儲存、再回頭指派」來回一趟。

維運上常見「設備建檔的同時就要配 IP」，且使用者期待「取消新增＝什麼都沒發生」：取消時新增的介面與指派必須一併消失。這與編輯既有資產的語意不同——編輯時指派是立即落地、立即推送 Kea（ADR-0011），取消對話框不會回撤已送出的指派。

替代方案：

- **先落地再指派**：按「指派 IP」時先自動建立資產與介面，再走現行指派；取消時補償刪除。會產生未完成的真實紀錄（關閉瀏覽器即殘留孤兒資產），「取消」不再是「什麼都沒發生」。
- **後端單一交易**：`POST /assets` 接受資產＋介面＋指派的嵌套輸入，單一交易寫入。原子性最好，但後端改動大，且讓新增（單一交易）與編輯（多次請求、部分落地）兩條路徑語意分歧。

## 決策

- 新增資產（以及編輯模式中新增的介面草稿）的指派在對話框內以**指派草稿**存在；儲存時依序落地（資產 → 介面 → 指派），取消即丟棄；落地前不呼叫指派 API、不推送 Kea。
- 編輯既有資產中**已儲存介面**的指派維持立即落地（不變）。
- 儲存時指派逐筆落地、遇錯即停、可重試；部分失敗後取消時，提供「繼續編輯／保留已建立內容／刪除已建立內容」選擇。
- 後端 API 不變。
- 草稿建立時以唯讀查詢做預檢（v4 用 `ip-candidates` 的 `query_status`；v6 用 `GET /subnets` 自行比對 CIDR；同介面同網段至多一筆），後端仍為最終權威。

## 理由

- 與既有介面草稿同一模式（`id === null`），前端一致、後端零改動。
- 「取消＝不送出任何請求」是唯一能保證不留孤兒紀錄的做法；補償刪除（先落地再指派）在失敗與中斷路徑上都會留下殘骸。
- 不採單一交易：改動大，且與既有編輯流程（多次請求、部分落地、可重試）不一致；若未來需要更強的原子性，可另案演進。
- 已知代價：指派落地時間延後，草稿期間位址可能被他人取得；儲存時以後端為權威、沿用「確認後原子移轉」（ADR-0007），維持既有防線。

## 後果

- 新增與編輯的指派落地時機不同（草稿 vs 立即）；由本 ADR 記錄，避免未來誤判為疏漏。
- 草稿預檢（v4 查詢狀態、v6 網段清單）可能過期，僅為提前攔阻；結構規則仍由後端把關（ADR-0006）。
- 部分失敗會留下已建立的資產與介面（與現行介面同步失敗的行為一致）；取消時以對話框讓使用者選擇保留或刪除。
- 未儲存資產的指派不進 `ip_assignments`，IP 清單在儲存前看不到該位址；草稿清單亦不提供「IP 管理」連結以免誤導。
