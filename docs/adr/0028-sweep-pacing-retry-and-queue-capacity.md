# ADR-0028：掃描逐筆節流、同輪重試與佇列容量推導

- 狀態：已接受
- 日期：2026-10-17

## 背景

場域實測（10.1.0.3、受管網段 10.1.0.0/16）證實：代理以 `rate_pps` 為批次大小、批內連發 1000 筆 ARP（8–10ms 廣播風暴）時，中後段設備的回覆在鏈路上確定性遺失——同一台設備（10.1.6.139）在批次位置 138 會回覆、位置 662 的探測則回覆從未回到代理主機（tcpdump 與 socket 對照）；批次實收率僅約六成，且同型設備在歷次掃描間「忽隱忽現」。另外，`/16` 單輪 `checked＋seen ≈ 65,696` 筆對 10,000 筆佇列容量，每輪固定丟棄 60,000 筆——被保留的永遠是位址尾段（10.1.234.100–255.99），多數位址的 `last_checked_at` 永不入庫。回覆窗「閒置」被背景 ARP 刷新，500ms 提早結束在平面 L2 永不觸發，掃描時間虛胖。

## 決策

1. **`AGENT_SWEEP_RATE_PPS` ＝ 逐筆送訊的每秒上限**（間隔 `1/rate` 秒）：批次概念退場；送訊期間以非阻塞方式即時收訊；全部送完後進入收尾回覆窗。
2. **收尾回覆窗閒置以「回覆」為準**（500ms；背景訊框不延長），2 秒硬上限不變。
3. **未回覆目標同輪重試一輪**（同速）。
4. **預設速率 1000 → 200**：實測 200pps 已涵蓋 10.1.6.139 類設備，且 `/16` 主掃＋重試 ≈ 11 分鐘，留在 900 秒週期內。
5. **推送佇列容量隨網段推導**：`(2 × host 數 ＋ 1,024)` 筆，下限 10,000、上限 1,048,576；滿載仍丟最舊。不做 checked/seen 優先級丟棄。

## 理由

- 遺失與「送訊密度」強相關（實測曲線 497pps→167、200pps→198、100pps→229、極慢 239），且對弱鏈路是確定性而非機率性——重試同速救不回、只有降速有效；故先修節流語意，再以重試回收瞬時遺失（實測 +16/1000）。
- 單輪 `checked＋seen ≤ 2 × host 數`，容量推導讓正常輪次零丟棄；latest-wins 語意下，長時離線的情境保留最新資料即為正確取捨，不必引入優先級丟棄的複雜度。
- 回覆窗改以回覆為閒置依據，讓掃描時間與實際回覆連動（修正前每批固定 2 秒）。

## 後果

- `/16`：主掃＋重試 ≈ 11 分鐘（200pps）；更慢的速率或更大的網段會拉長掃描，選值時以「主掃＋重試 ≤ 週期」為預算。
- 記憶體：佇列容量上限 1,048,576 筆（/16 實際 132,092）；`HashSet` 目標集 /16 ≈ 0.8MB。
- 極慢鏈路設備（實測 ≤50pps 才回）仍可能落在 200pps 之外；以調低 `AGENT_SWEEP_RATE_PPS` 因應（自適應速率另案）。
- 既有真機測試與 `checked`／`seen` 回報語意不變。
