# ADR-0014：觀測與宣告分離（唯讀影子層）

- 狀態：已接受
- 日期：2026-10-06

## 背景

本系統現有的位址資料是「宣告」：Assignment（意圖）與 Reservation 以 asset-nest 為真實來源（ADR-0002、ADR-0005），且明文只記現況、不留歷程。新的網路觀測能力會持續得到「某位址某時刻被誰使用／是否可見」的事實，這些事實與宣告可能不一致（宣告 MAC 未出現、其他 MAC 在用、未指派位址有主）。直覺做法是以觀測自動修正宣告、或把觀測併入指派資料，但觀測本質上有盲點：Windows 預設不回應 ICMP、跨路由不可見、掃描本身可能失敗；用不可靠的證據改寫真實來源，會讓「宣告」失去可信度。

## 決策

- **觀測是一層唯讀的影子資料**：保存於自己的現況與事件資料中，永不修改 Assignment、Reservation、Asset／Interface。
- **不一致一律是衝突標記**：沿用 ADR-0006 的分界——標記提示、不阻擋；新增 `ObservedMacMismatch`（已指派位址出現非宣告 MAC）與 `ObservedOnUnassigned`（未指派且非池內位址有主）。池內位址被 DHCP 動態使用屬正常，不算衝突。
- **刪除與釋出的決策由人執行**：系統只提供資訊（「最後可見」欄位、篩選、刪除／取消指派的確認框提示），不自動刪除資產或釋出位址。

## 理由

- 「沒看到」不等於「不存在」：觀測盲點造成的誤判若會自動改資料，代價是刪錯資產、釋出使用中的 IP。
- 宣告必須保持單一寫入者與可信度（延伸 ADR-0002 的真實來源精神）；觀測資料可被清除而不影響宣告。
- 衝突計數的增加提醒管理者注意，但不阻止任何既有操作，與系統既有 ethos 一致。

## 後果

- API／UI 不得提供「以觀測覆寫宣告」的操作；未來若要做自動化，需另案與新 ADR。
- 觀測保留期到期清除事件時，宣告資料完全不受影響。
- 衝突標記的呈現需與既有徽章／警示／計數一致。
