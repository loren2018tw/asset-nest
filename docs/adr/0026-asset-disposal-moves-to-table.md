# ADR-0026：資產報廢以獨立資料表搬移，不採狀態欄位

- 狀態：已接受
- 日期：2026-10-12

## 背景

資產需要「報廢」：設備損壞或逾齡汰換後移出在管清單，但財管查核需要資料留存。兩種做法：

- **狀態欄位**：`assets` 加 `disposed_at`，清單預設過濾。關聯資料（介面、指派、借還）完整保留、可完整復原，但所有既有查詢（清單、搜尋、匯出、清冊稽核、Kea 同步、指派入口）都必須記得排除已報廢，漏一處就是錯誤資料；且與財管「財產帳／報廢清冊」分離的慣例不符。
- **搬移**：報廢＝整列複製進 `disposed_assets`（＋報廢日期）後自 `assets` 刪除。`assets` 維持「在管資產」單一語意，既有功能零改動；代價是外鍵連動（介面、指派、借還紀錄）與復原不完整。

## 決策

- 採**搬移**：`disposed_assets` 保存資產欄位複製＋`asset_id`（原資產 id）＋`disposal_date`；報廢時原列自 `assets` 刪除（FK CASCADE 連動刪除介面、指派與借還紀錄）。
- 報廢即**釋出 IP**：不保留 MAC 快照；受管網段的「保留」推送 Kea 刪除（沿用 ADR-0011 的單筆推送；失敗不阻擋本地儲存、僅回警示）。
- **復原**＝將欄位搬回 `assets`（沿用原 id 與 `created_at`）並刪除報廢紀錄；介面與 IP 指派**不**回復。報廢歷程不保留。
- 出借中不可報廢（409）；報廢日期必填、不可為未來、可回填過去。
- 已刪除資產不推送 Kea 的既有缺口不在本決策範圍（另案）。

  > **後續修訂（2026-10-14）**：`DELETE /assets/{id}`（含草稿取消的「刪除已建立內容」）的 Kea 推送已由 ADR-0027 補齊。

## 理由

- 「在管資產」單一語意讓所有既有查詢自動正確；狀態欄位需要逐一改查詢，成本高且容易遺漏。
- 與財管實務一致：報廢清冊獨立於財產帳，可獨立搜尋、分頁與復原。
- 觀測資料以 MAC／網段為鍵，不受搬移影響；MAC 歷史可事後由觀測查得，故不快照。
- 復原不回復介面與指派：介面已隨刪除釋出、IP 可能已被重新指派；「復原資產、重建介面」比「還原到某時點」語意單純且可實作。

## 後果

- 復原後的資產沒有介面與 IP 指派，需重新建立（使用者已知悉；確認框明示）。
- 復原後不留「曾被報廢」歷程；若未來需要，另立 append-only 機制。
- 清冊稽核「系統有」側自動不含報廢資產；清冊仍列已報廢財產編號時會顯示「清冊有、系統沒有」，屬實。
- 報廢時 Kea 推送失敗僅警示（ADR-0011），本地搬移已完成。
